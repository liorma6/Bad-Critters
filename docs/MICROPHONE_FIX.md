# Microphone investigation and fix — 2026-09-27

The local recorder now distinguishes acquisition, analysis, recording, finalization, and decoding. Successful permission or nonempty encoded bytes alone cannot enable acceptance.

## Confirmed findings and limits

- The previous implementation created/resumed its AudioContext **after** awaiting microphone permission. Resume was unbounded, and the UI showed the same permission message while waiting for either acquisition or resume. It also cancelled pending acquisition on `visibilitychange`; native permission UI can temporarily hide a page. These implementation defects are corrected and regression-tested with delayed permission and a simulated lost-gesture restriction. They are not claimed as proof of the user's specific device failure.
- The old basic mode always requested noise suppression, echo cancellation and automatic gain control. It had no truly unprocessed comparison path. Its linear `RMS * 5` meter barely displayed low input, and a nonempty silent/corrupt Blob counted as a successful take.
- In the **actual in-app preview**, the old UI stayed indefinitely at permission waiting with no console error. With diagnostics installed, AudioContext reached `running`, but `getUserMedia` did not resolve within 20 seconds. No audio track or recorder was created. The page reported secure context, available mediaDevices, top-level browsing (`iframe=false`), and microphone policy allowed. The local production header is `Permissions-Policy: microphone=(self)`. This observed failure is at the browser acquisition boundary, before the analyser/recorder. Its host-side cause remains unconfirmed and cannot be repaired from game JavaScript.
- In **installed Chrome with no fake-media flags**, a real system-input probe returned a live, enabled, unmuted track and a running context. It captured 65,138 bytes over 4.02 seconds; peak input RMS was 6.68e-4 and decoded peak-window RMS was 7.75e-4. No recording was saved, played, or uploaded. This establishes nonzero system-input capture in Chrome, not a verified spoken sentence or the identity of the user's intended physical microphone. Safe diagnostics are in `microphone-physical-probe.json`.
- Analyser output being unconnected was **not** the defect: a source-connected analyser can operate without an output connection. Live microphone audio remains disconnected from speakers. [MDN AnalyserNode](https://developer.mozilla.org/en-US/docs/Web/API/AnalyserNode)

## Changed behavior

1. Record/Retry creates and resumes the context directly within the click. Acquisition and context startup have bounded, distinguishable failures. Returned track health is checked. Source, analyser, processing nodes, recorder and chunks belong to one capture session; a late permission/resume/decode cannot release a newer session.
2. The default path records the returned input stream directly. Both browser cleanup and gentle filter/compressor are optional. The meter samples independently of animation frames and uses a logarithmic display suitable for quiet input. Three seconds without measurable input displays a Hebrew message with Retry/input-selection actions; it does not prematurely stop quiet speakers.
3. Stop waits for final data, releases hardware, decodes the complete Blob, and checks short-window AC energy. Digital silence, DC, missing data, processing silence and decode failures cannot become accepted takes. Signal validation and actual decoded duration are stored alongside accepted audio. Pauses do not dilute a short spoken passage into silence. Existing saved takes remain compatible.
4. Multiple inputs are offered after permission. The system default is initial; an available prior choice is reused locally. Switching releases the old capture and enables recording on the selected input without reload. Removed selections fall back safely. Device labels stay in the local selector; diagnostics contain no device IDs or raw recordings.
5. Expandable Hebrew diagnostics expose capture stage, track readyState/enabled/muted, context state, input RMS, recorder state/MIME, byte count, environment/policy flags, decoded signal and actionable errors. Exceptions retain error names/stages rather than private device messages. No live microphone monitoring is connected to speakers.

## Validation

- 60 Node checks, including new quiet-signal and silence/DC rejection checks, plus the existing game and storage checks.
- 25 focused Chrome browser checks passed: seven existing dubbing flows, ten new capture checks, and eight game voice-playback checks. The new deterministic capture tests feed a generated 220/660 Hz WAV through Chrome's simulated capture driver and actual getUserMedia/MediaRecorder/decoder. They assert meter activity, decoded signal and the expected 220 Hz component, playback analyser energy, listen-before-accept, IndexedDB persistence, reload playback and in-game playback. Raw capture, filter/compressor, browser cleanup and combined processing all pass. A separate near-silent synthetic stream passes; digital silence fails and retries in place.
- Nine additional Chrome failure checks passed, bringing the focused browser total to **34 passed**. They cover unavailable/absent devices, cancelled-session resume, disabled tracks, silent and disconnected enhancement, microphone Permissions Policy, an acquisition that never returns, and cleanup without live speaker connections. The other capture suite also tests suspended context and corrupt decoding. A disconnected destination initially produced no bytes rather than an encoded silent file; the test fixture was split to verify both distinct failures. Machine-readable outcomes: `microphone-browser-summary.json`.
- Synthetic driver/oscillator tests are explicitly labeled **SYNTHETIC**. Measured playback graph energy is not a human listening test. The real system-input probe is documented separately above. iOS/Safari and Android hardware/encoders remain untested; MIME support is detected, and incompatible decoded output fails visibly.
